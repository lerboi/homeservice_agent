#### ❌ R2 ("issue 2"). New Twilio numbers BYPASS the FastAPI webhook → owner-pickup / VIP / schedule / outbound-caps DEAD for every new tenant
**Severity: HIGH. NOT DONE — GATED. Do NOT blind-apply: a wrong fix breaks ALL new-tenant inbound calls (strictly worse than today, where the AI at least answers).**

**What it is (verified first-hand 2026-06-19):**
- `provisionPhoneNumber` (`src/app/api/stripe/webhook/route.js:66`) configures every new number with a **trunk association ONLY** — SG path `route.js:104-114` and US/CA path `route.js:157-162` both call `client.trunking.v1.trunks(process.env.TWILIO_SIP_TRUNK_SID).phoneNumbers.create({ phoneNumberSid })`. There is **no `voiceUrl`/`voiceFallbackUrl`/`smsUrl`** set anywhere in the function (whole-file grep confirms).
- **Twilio routing fact** (per IncomingPhoneNumber + Elastic SIP Trunking docs): a number with a `trunk_sid` **ignores all of its voice URLs** and routes inbound to the trunk's Origination URI (→ LiveKit), **bypassing `/twilio/incoming-call`**.
- The FastAPI webhook (`livekit-agent/src/webhook/twilio_routes.py`) is the **ONLY** place that implements VIP routing (`_is_vip_caller`), working-hours schedule (`evaluate_schedule`), owner-pickup parallel-ring (`_owner_pickup_twiml`), and the monthly outbound-minute cap (`check_outbound_cap`). New numbers never hit it, so **none of these run for any tenant provisioned after the regression.** (The agent-side subscription gate in `agent.py` is separate and still blocks non-payers.)

**Why it's a regression, not an unbuilt feature:** the intended design IS webhook-routed — `provisionPhoneNumber` is DOCUMENTED to set the voice URLs (`.planning/ROADMAP.md:766`; `My Prompts/Architecture/Call Routing System.md`), and Phase-40 commit `d7f24ef` added exactly that wiring but is **NOT an ancestor of HEAD** (lost in a history divergence; current provisioning descends from `7e6e293`, which only added the trunk association). `scripts/cutover-existing-numbers.js` sets the voice URLs on EXISTING numbers, so only manually-cutover numbers get webhook routing today.

**The fix (Design A — restore webhook routing):**
1. In `provisionPhoneNumber` (BOTH SG and US/CA paths): after obtaining the SID, `client.incomingPhoneNumbers(sid).update({ voiceUrl: ${RAILWAY_WEBHOOK_URL}/twilio/incoming-call, voiceFallbackUrl: ${...}/twilio/dial-fallback, smsUrl: ${...}/twilio/incoming-sms })`, AND **explicitly disassociate the number from the trunk** (`trunk_sid` takes precedence over `voiceUrl`, so leaving it nullifies the fix). Recover the URL construction via `git show d7f24ef:src/app/api/stripe/webhook/route.js`.
2. `scripts/cutover-existing-numbers.js` (~lines 82-86) sets voice URLs but DELIBERATELY KEEPS the trunk association ("D-21 rollback safety net") — **unsound** given trunk-wins precedence; it must ALSO disassociate the trunk.
3. Add `RAILWAY_WEBHOOK_URL` to the Next.js `.env.example` (currently only in `livekit-agent/.env.example`).
4. Fix the **inverted precedence claim** in `My Prompts/Architecture/Call Routing System.md:105` ("Twilio prioritizes voice_url over SIP trunk" — BACKWARDS; the trunk wins).
5. Fail-safe: if `RAILWAY_WEBHOOK_URL` is unset, do NOT set a broken `voiceUrl` (keep current behavior).

**HARD PREREQUISITES (this is the gate):**
- **`RAILWAY_WEBHOOK_URL` MUST be set in Vercel production** — unset → pointing numbers at `voiceUrl` breaks inbound entirely. Not in the Next.js `.env.example`; **confirm in Vercel env first.**
- **Verify live Twilio routing** for the cutover'd number (`+14783755631`, SID `PNd63102b147149f82cb6bf27074cc14d6`): does it show `voice_url` set with `trunk_sid` CLEARED? Prod Twilio creds live in Railway/Vercel (not local `.env`) → needs the user.

#### ⚠️ R1 ("issue 1"). Owner-pickup no-answer DROPPED the caller — fix WRITTEN but UNCOMMITTED
**What it was:** in owner-pickup routing, `twilio_routes.py` returns a parallel-ring `<Dial action="/twilio/dial-status">` (`_owner_pickup_twiml`). On no-answer/busy/failed, `dial_status` returned an **empty `<Response/>`** — and per Twilio's `<Dial action>` semantics the action TwiML takes full control of the still-connected caller leg, so an empty response **hangs up the caller**. The intended "owner doesn't pick up → AI takes over" never executed (`dial_status` only wrote `routing_mode='fallback_to_ai'` without acting on it). Lost-job bug.
**Fix (code written):** `dial_status` now returns `_ai_sip_twiml()` (the exact TwiML the working direct-AI path uses) when `final_mode == "fallback_to_ai"`; `final_mode` is computed BEFORE the DB write so AI fallback fires even if that write fails. Tests updated (`tests/webhook/test_routes.py`).
**⚠️ STATUS CORRECTION (verified 2026-06-19): NOT committed.** The change exists only as **uncommitted modifications** in the livekit working tree (`src/webhook/twilio_routes.py`, `tests/webhook/test_routes.py`) — it was **not** part of WAVE 3's commit `9dea46e` and is **not** pushed (confirmed: both files show modified-unstaged on `main`). No live effect yet anyway (owner-pickup is unreachable until R2). **Action:** commit + push it alongside R2's rollout — until then it's at risk of a stray `git checkout`/`stash`. (Note: `test_incoming_call_vip_lead` is a pre-existing/stale failure — Phase-59 disabled lead-based VIP — unrelated to this change.)
