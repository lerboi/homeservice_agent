## CRITICAL — security

### S1. All 7 SECURITY DEFINER RPCs are executable by `anon` (live, today)
Root cause: migrations 027/033/062/065 ran `REVOKE … FROM PUBLIC`, but Supabase grants EXECUTE to `anon`/`authenticated` **explicitly** on every new function — `REVOKE FROM PUBLIC` is a no-op against those grants. Confirmed live via `has_function_privilege`. The anon key ships in the browser bundle, so anyone can call via `/rest/v1/rpc/...`:

| Function | Anon attack |
|---|---|
| `book_appointment_atomic` | Insert appointments into **any tenant's** calendar — block a competitor's entire schedule (denial of bookings), inject junk |
| `assign_sg_number` | Drain the shared SG phone inventory onto arbitrary tenant_ids — onboarding DoS + cost-bearing Twilio numbers leaked |
| `set_primary_calendar` | Flip any tenant's primary calendar → bookings sync to the wrong/disconnected calendar |
| `record_call_outcome` | Inject customers/inquiries/jobs into any known tenant's CRM (needs valid tenant UUID) |
| `merge_customer` / `unmerge_customer` | Corrupt/destroy CRM data (needs tenant + customer UUIDs) |
| `increment_rate_limit` | Pre-inflate any rate bucket → lock victims out of contact/OTP flows |

**Fix (one migration):** for every SECURITY DEFINER function: `REVOKE EXECUTE … FROM PUBLIC, anon, authenticated; GRANT … TO service_role;` (068 already does this for the two lock RPCs — extend the idiom). All are called only via service-role clients, so no app breakage. Also add `SET search_path = public, pg_temp` to each (all 7 have mutable search_path).

### S2. `oauth_refresh_locks` is wide open (RLS disabled + anon INSERT/UPDATE/DELETE grants)
Confirmed live. Anyone with the anon key can DELETE a legitimate refresh lock (re-opening the double-refresh race — for Jobber's single-use refresh tokens that **bricks a tenant's integration**) or INSERT permanent lock rows (blocks all Xero/Jobber refreshes — integration outage). Fixed by applying 068 (§ B2).

### S3. Onboarding checkout likely broken: `ui_mode: 'embedded_page'` under the Basil API pin — VERIFY IMMEDIATELY
`stripe` SDK v21 natively pins `2026-03-25.dahlia`; `src/lib/stripe.js:9-13` overrides to `2025-03-31.basil`; but `onboarding/checkout-session/route.js:103` sends `ui_mode: 'embedded_page'` — a **dahlia-only** enum (Basil expects `'embedded'`). The enum landed pre-pin; the Basil pin landed 2026-06-03. If confirmed, **new-customer signup fails at checkout creation**. Fix: test-mode verify; either pin dahlia (SDK-native; webhook already reads both field shapes) or revert to `ui_mode: 'embedded'`.

### S4. Voice pipeline: missing `DEEPGRAM_API_KEY`/`ELEVEN_API_KEY` kills every call silently while healthcheck stays green
`deepgram.STT` / `elevenlabs.TTS` are constructed per call inside `entrypoint()` (`agent.py:566,588`) and raise at call time; no boot preflight; `/health` is pure liveness. Railway keys were noted as **pending** — if still unset, every inbound call rings then dies with no audio, and the deploy looks healthy. Same class: an ElevenLabs voice_id missing from "My Voices" hard-fails every call at TTS time. Fix: fail-fast preflight in `__main__` (assert keys, optionally probe `/v1/voices`).

## HIGH

### H1. `past_due`/`unpaid` is never enforced anywhere — confirmed across all 3 implementations
- `src/proxy.js:112-133` queries subscription status then **does nothing** (comment admits it; also burns a service-role query per dashboard nav).
- `src/lib/subscription-gate.js` excludes past_due ("3-day grace") and has **zero callers**.
- LiveKit `agent.py:901-909` + `twilio_routes.py:186-195` block only canceled/paused/incomplete — past_due answers calls forever.
- `BillingWarningBanner.js:69` **hides itself after the 3-day grace** expecting a middleware redirect that doesn't exist — past-grace tenants see no warning at all (and both billing banners have dismiss buttons despite "not dismissible" specs).
Net: stop paying → keep full dashboard + AI receptionist (Deepgram/GPT/ElevenLabs/Twilio costs on you) until the numeric call cap. Fix: enforce `past_due` beyond grace in agent.py + twilio_routes.py (single shared check), make the banner persist, delete or re-enable the proxy gate.

### H2. Stripe webhook can permanently lose events (false 200 inside the 10-min claim window)
`webhook/route.js:174-177`: a duplicate delivery that fails to claim (live claim <10 min) is acked 200. If the first delivery died un-gracefully (function timeout — realistic for `handleCheckoutCompleted`'s Twilio purchase + SIP association), Stripe's retry gets the 200 and **stops retrying forever**; the row sits `processed=false` and nothing sweeps it. Lost fulfillment/cancellation/usage-reset, silently. Fix: return 500 when claim fails and `processed=false`; only ack on `processed=true`; add a reconciliation cron. (Note: 56 live webhook rows are all `processed=false` — the deployed build doesn't use the claim at all yet.)

### H3. Annual-plan overage is likely unbillable (silently swallowed)
The same monthly-interval overage price IDs are attached to annual subscriptions (`stripe-plans.js:19-23`); Stripe requires flexible billing mode for mixed intervals, which neither checkout sets, and the attach error is swallowed as "non-fatal" (`webhook/route.js:350-353`). Meter events record but never rate. Fix: test-mode verify; set `billing_mode: 'flexible'` or create annual overage prices; alert on attach failure.

### H4. Failed Stripe meter events are permanently lost
`livekit-agent/src/post_call.py:182-183` prints and moves on; replay is structurally impossible (`usage_events` PK already consumed, so re-runs skip the meter branch). Every transient failure on an over-quota call = $1.50–$2.48 unbilled. Fix: reconciliation cron (usage_events beyond limit vs Stripe meter summaries) or durable outbox; `identifier=overage_{call_id}` already makes posting idempotent.

### H5. Twilio numbers never released on churn
The `canceled` branch (`webhook/route.js:497-509`) only deletes billing notifications. No `incomingPhoneNumbers().remove()`, no SIP de-association, no `phone_inventory` un-assignment anywhere; the Twilio SID isn't even persisted. ~$1.15/mo per churned US/CA tenant forever; finite SG inventory consumed permanently. Also: a crash between Twilio purchase and `tenants.update` in checkout fulfillment orphans a number (retry buys another). Fix: release with retention window in the canceled branch + weekly reconciliation cron.

### H6. Calendar mirror has multiple ways to freeze silently → systematic double-bookings
- **Outlook delta sync has no 410/resync recovery** (`outlook-calendar.js:281-302`): one expired deltaLink and the Outlook mirror freezes forever (Google has the 410 fallback; Outlook has nothing).
- **Sync windows are anchored at connect time and never re-extend** (Google `timeMin/timeMax` at connect, `google-calendar.js:244-253`; Outlook same): ~6 months in, incremental syncs report nothing — no external busy data at all.
- **Outlook subscription renewal PATCHes a dead subscription** (404 → logged → retried daily, never recreated; `outlook-calendar.js:370-386`). Google recreates; Outlook doesn't.
- **No daily pull-sync sweep** exists; webhooks are the only sync path and failures only log.
A frozen mirror = the AI offers slots the owner's real calendar has busy. Fix: 410-catch + resync for Outlook, recreate-on-404, scheduled monthly full resync (clear token, wipe provider rows, resync), daily sweep cron with alerting.

### H7. Python refresh-lock loser re-refreshes after a 3s poll → bricks Jobber connections
`livekit-agent/src/integrations/{jobber,xero}.py`: the lock loser polls 3s then falls through to its **own** wire refresh with the already-consumed (single-use) refresh token → 400 → `error_state='token_refresh_failed'` → keep-fresh cron skips the row → sticky "Reconnect required" from a transient slow refresh. JS deliberately throws instead. Fix: mirror JS (give up on poll timeout) or extend the poll window past the winner's 10s read timeout; don't set error_state on this path.

### H8. Voice post-call: 8s budget vs 5s Layer-2 triage can starve inquiry creation + emergency owner alerts
`agent.py:774-802` wraps the whole pipeline in `wait_for(8.0)`; Layer-2 Groq triage holds a 5.0s timeout and the Stripe meter call has **no explicit timeout** (default ~80s read). Slow triage + normal DB latency → `record_outcome` (§6.5) and owner notifications (§7) cancelled: no inquiry row, no EMERGENCY alert — the 2026-04-21 incident class. Fix: Layer-2 timeout ≤2.5s, explicit Stripe timeout, and/or send notifications before triage with urgency-upgrade.

### H9. Dashboard data-loss/UX highs (all confirmed)
- **Invoices/estimates lists hard-capped at 50** — API paginates and returns `total_count`; `useDocumentList.js` ignores both; tabs show true counts (e.g. "80") while 30 rows are unreachable.
- **JobFlyout transcript + recordings dead**: `src/lib/jobs.js:39,84` never selects `transcript_*`/`recording_storage_path` → "No transcript available" always; only legacy `recording_url` rows play. `job_type` chip never renders (column doesn't exist).

- **No AbortController on nearly all fetches** (calls/jobs/customers/customer-detail/CommandPalette/merge-typeahead) — stale-response races; only `calendar/page.js` does it right.
- **Mobile create-FABs overlap the BottomTabBar** on invoices + estimates (`bottom-6` vs the 64px bar) — covers the "More" tab on every phone.
- **UnmergeBanner can never appear on revisit**: gated on `customer.merged_source_info`, which no API ever returns — the advertised 7-day undo affordance vanishes after the post-merge redirect.
