The caller's mic is fully MUTED during the ~5–6s greeting.** **What:** input is disabled (not buffered) during greeting playout as an echo defense. **Evidence:** `agent.py:1067` (`set_audio_enabled(False)`). **Why it matters:** an emergency caller who blurts "I have a burst pipe!" over the recording disclosure is not heard and must repeat it after the greeting — mildly frustrating exactly when speed matters. **Fix:** prefer buffering input during the greeting (or unmute a beat earlier) so early speech is captured, keeping the echo defense via `allow_interruptions=False` + the unmute-timeout already in place.

- **❌ LK-C3. A subscription-blocked caller is hung up on right after the greeting, with no explanation.** **What:** the gate check runs in the backgrounded DB task that resolves AFTER the greeting fires, then bluntly `remove_participant`s the caller. **Evidence:** `agent.py:988-998` (silent remove inside `_run_db_queries`, created `:1011`; greeting at `:1079`). **Why it matters:** a homeowner hears "How can I help you?", maybe starts talking, then the line drops — looks like a broken number (affects only past-due-beyond-grace tenants, so low blast radius). **Fix:** speak a brief "this number is currently unavailable, please try again later" before disconnecting, and ideally evaluate the gate before the greeting.

### C — Reliability & correctness bugs

- **❌ LK-R1. The conversational LLM runs at default temperature (1.0) despite an ~8K-token anti-hallucination prompt.** **Evidence:** `agent.py:615-619` (`openai.LLM(...)`, no `temperature`) vs `lib/triage/layer2_llm.py:51` (`temperature=0` — they know the knob). **Why:** higher sampling temperature directly undermines the instruction adherence the entire prompt depends on, raising the odds of a fabricated "you're all set"/"available" on some calls — the product's #1 catastrophic failure. **Fix:** pin temperature ~0.2–0.4 on the session LLM (one line).

- **❌ LK-R2. Spoken booking/availability confirmation has no runtime backstop — anti-fabrication is prompt-only.** **Evidence:** `prompt.py:297-333` (OUTCOME WORDS) + `:1011-1022` (NO DOUBLE-BOOKING) are instructions only; the DB write is safe (needs a real `slot_token`) but nothing cross-checks a SPOKEN "confirmed" against an actual booking result. **Why:** a single fabricated confirmation = a caller who thinks they're booked and a job that never happens, with no detection. **Fix:** add an end-of-turn or post-call reconciliation that flags a settled outcome word ("booked"/"all set"/a specific time) in the transcript with no matching successful `book_appointment`, surfacing it as an owner alert instead of a silent loss.

- **❌ LK-R3. Emergency triage has two fail-UNSAFE paths.** **What:** (a) Layer-2 depends on a separate Groq LLM that fails SILENTLY to "routine"; (b) Layer-3 escalates on the AGENT's own speech, not just the caller's. **Evidence:** `lib/triage/layer2_llm.py:34` (api_key default `''`), `:56-57` (bare except → `{'urgency':'routine'}`); `lib/triage/classifier.py:34-37,47-50` pass the FULL transcript to `apply_owner_rules`, `lib/triage/layer3_rules.py:52-59` regex-matches the full transcript — contrast `layer1_keywords.py:25-42` which strips AI lines. **Why:** a descriptive emergency without a keyword ("basement is filling with water", "I smell burning") with Groq down/misconfigured is labeled routine → owner gets a non-urgent alert for a real emergency; and a routine call escalates to a FALSE emergency whenever the agent merely says a tenant-tagged service name, eroding trust in the flag. **Fix:** bias the Layer-2 fallback toward escalation (and/or alert on Groq failure); make Layer-3 match caller-only text like Layers 1/2.

- **❌ LK-R4. Misdial/voicemail notification spam.** **What:** owner notifications fire for sub-15s empty-transcript calls. **Evidence:** `post_call.py:328` has no duration gate; contrast `record_outcome` gate at `:276` and the recovery cron skip at `route.js:98`. **Why:** a 5–14s misdial sends "New inquiry — Unknown, General inquiry" via SMS+email with no CRM row behind the link, training owners to ignore the very alerts they pay for. **Fix:** add a <15s minimum-duration guard to the owner-notification block.

- **❌ LK-R5. Recovery SMS can orphan in 'pending' and never be retried.** **What:** the fire-and-forget task writes `recovery_sms_status='pending'` before sending; if the call ends first, no cron branch reclaims 'pending'. **Evidence:** `book_appointment.py:611` (unowned `create_task`), `:123` ('pending' write); cron reclaims only NULL (`route.js:69`) and 'retrying' (`:178`); the unowned-task hazard is even documented at `agent.py:862-866`. **Why:** a caller whose slot was taken right before hangup gets no follow-up, a silently dropped lead. **Fix:** await the recovery send during shutdown, or have the cron reclaim 'pending' rows older than N minutes.

- **❌ LK-R6. Calendar push (Google/Outlook) is fire-and-forget with no retry or reconciliation.** **Evidence:** `calendar_push.py:54-55`, `google_calendar.py:188-189`, `outlook_calendar.py:148-149` swallow all failures; `book_appointment.py:764-775` fires via `create_task` with no result tracking; `post_call.py` has no calendar reconciliation. **Why:** a transient calendar-API outage or unrecoverable token at booking time means the appointment never lands on the owner's calendar — for a contractor who runs their day from Google Calendar, that's a confirmed-but-invisible job. **Fix:** add a calendar-push outbox/retry (or a cron that finds appointments with a connected calendar but `external_event_id IS NULL`), mirroring the `stripe_meter_failures` pattern.

- **❌ LK-R7. `dial_timeout_seconds` present-but-NULL yields `<Dial timeout="None">`.** **Evidence:** `webhook/twilio_routes.py:224,280` (`tenant.get('dial_timeout_seconds', 15)` — `.get(key, default)` returns the NULL, not the default). **Why:** malformed TwiML on the owner-pickup/VIP paths; Twilio may reject or ignore the attribute. **Fix:** `tenant.get('dial_timeout_seconds') or 15`.

- **❌ LK-R8. TwiML injection / toll-fraud vector: caller `From` is interpolated unescaped.** **Evidence:** `webhook/twilio_routes.py:64-77` (`callerId="{caller}"` and `<Number>{n}</Number>` f-string); `lib/phone.py:16-41` does no character validation. **Why:** a SIP-originated crafted `From` with quotes/angle brackets could inject TwiML verbs (e.g. redirect the `<Dial>` → toll fraud). Low probability, but it's unescaped attacker-influenced data in an XML response. **Fix:** XML-escape `from_number`/pickup numbers (`xml.sax.saxutils.quoteattr`/`escape`) before interpolation, and validate the normalized number shape.

- **❌ LK-R9. Status-filter inconsistency → spurious `slot_taken`.** **What:** availability tools exclude both `cancelled` and `completed` from the busy set, but the atomic RPC + GiST constraint + the `slot_taken` recalc treat only `cancelled` as free. **Evidence:** `_availability_lib.py:201-202` (`.neq cancelled .neq completed`) vs `book_appointment.py:553` (`.neq cancelled` only) and the `appointments_no_overlap` constraint `WHERE status<>'cancelled'`; `completed` is a live status (10 rows in prod). **Why:** a future `completed` appointment is OFFERED by `check_slot` then REJECTED by the RPC as "just booked by someone else" — a confusing dead-give-away on a slot nobody actually took. **Fix:** pick one busy-set rule everywhere (cancelled-only is safest — a future completed slot is genuinely occupied) and add a test that a future completed appointment isn't offered.

- **❌ LK-R10. `book_appointment` lacks the top-level try/except its sibling read tools have.** **Evidence:** `book_appointment.py:456-462` (unguarded tenant `.single()`) and `:738-742` (unguarded post-commit `booking_outcome` update) vs the wrapper try/except in `check_slot.py:87-102`. **Why:** an exception on the post-commit update would escape the tool AFTER the slot is actually booked → dead air / a raw framework error at the worst possible moment (the caller expects "you're booked"). **Fix:** wrap the body in a top-level guard returning a `booking_failed` STATE+DIRECTIVE (apologize + capture_lead/transfer), matching the read tools.

- **❌ LK-R11. Owner SMS/email links default to `https://localhost:3000` if `NEXT_PUBLIC_APP_URL` is unset in the agent's Railway env.** **Evidence:** `post_call.py:371`. **Why:** every owner alert would ship a dead localhost link. **Fix:** fail loud at boot if unset (see LK-R15), or default to the prod host `https://www.voco.live`.

- **❌ LK-R12. Unescaped HTML interpolation of caller-influenced fields into the owner email body.** **Evidence:** `notifications.py:172-181` (f-string injects `caller_name`/`job_type`/`service_address`/`from_number`). **Why:** low real-world risk (values come from STT) but it's unescaped user-influenced content in HTML. **Fix:** HTML-escape the interpolated fields.

- **❌ LK-R13. Xero phone matching is over-broad (wrong-customer disclosure) and silently misses large orgs.** **Evidence:** `integrations/xero.py:344-345` (fetches only the default page, ≤100 contacts) + `:359-396` matching on last-10 OR last-7 digits (`:394`). **Why:** the last-7 OR-match can hit a DIFFERENT customer (same local digits, different area code) and surface their outstanding balance to the caller; orgs with >100 contacts silently never match. **Fix:** match on full E.164 / last-10 only (drop last-7), and paginate or log an explicit ">100 contacts, match unsupported" signal.

- **❌ LK-R14. Owner-pickup→AI-fallback creates two unreconciled `calls` rows.** **Evidence:** the webhook upserts `on_conflict='call_sid'` (`webhook/twilio_routes.py:91-97`); the agent upserts `on_conflict='call_id'` (`agent.py:887-900`) with no shared key. **Why:** one physical call becomes two CRM rows that never reconcile, inflating counts and splitting routing metadata from the conversation record. **Fix:** thread a single shared identifier across the webhook and agent inserts.

- **❌ LK-R15. Boot preflight checks only 3 of ~8 call-fatal env vars.** **Evidence:** `agent.py:1236-1238` checks OPENAI/DEEPGRAM/ELEVEN; `supabase_client.py:13-16` raises only at first call (missing `SUPABASE_SERVICE_ROLE_KEY`/`NEXT_PUBLIC_SUPABASE_URL` → every tenant lookup raises), `layer2_llm.py:34` silently degrades without `GROQ_API_KEY`, Sentry is a silent no-op without `SENTRY_DSN` (`agent.py:28-32`). **Why:** the preflight's own rationale (prevent connect-then-die / silent degradation / no observability) applies equally to the unchecked keys; a deploy missing them starts green and fails on the live path. **Fix:** broaden the preflight to all call-fatal vars and emit a startup WARNING when `SENTRY_DSN` is unset; restore/commit `.env.example` as the canonical manifest (it was deleted in the working tree).

- **❌ LK-R16. The subscription gate (decides whether a caller is answered) has ZERO tests.** **Evidence:** `lib/subscription_gate.py:29-51` (pure 3-day-grace date math whose PRIOR bug the module docstring itself describes); no `tests/*subscription*` exists. **Why:** a bug here either blocks a paying customer's calls or comps a non-payer — and it's trivially unit-testable. **Fix:** add ~30 lines of tests (grace boundary, unparseable-date fail-open).

- **❌ LK-R17. Healthcheck doesn't verify the worker can answer calls.** **Evidence:** `Dockerfile:16` → `webhook/app.py:62` `/health/db` only checks the FastAPI daemon thread + a `tenants` SELECT; a hung/crashed LiveKit worker stays green (acknowledged at `agent.py:1232-1235`). **Why:** the orchestrator won't restart a zombie worker, so calls silently fail while the probe is healthy. **Fix:** add a worker-liveness signal to the health probe (e.g. last-job heartbeat).

- **❌ LK-R18. Migration ledger drift + deleted env manifest (cross-repo hygiene).** **What:** migrations 073/074/075 are applied (or about to be) to prod but the SQL files are untracked/uncommitted and `list_migrations` returns `[]`; `.env.example` is deleted in the agent working tree. **Why:** prod schema has no reproducible source of truth (DR/staging parity risk) and a new deployer has no authoritative env-var list. **Fix:** commit the working trees, reconcile the migration ledger so applied schema is reproducible, and restore `.env.example`.

### D — Over-engineered for a 1–5-person shop (complexity to cut or gate)

- **❌ LK-O1. The zone / zone-pair travel-buffer matrix is fully built but completely DORMANT.** **Evidence:** `slot_calculator.py:42-96` (`_get_travel_buffer_mins` zone branches) + the `zones`/`zone_travel_buffers` per-availability-call fetch (`agent.py:927-941`) — but `candidate_zone_id` is never passed and bookings always insert `zone_id=None`, so every booking collapses to the flat default. **Why cut:** a solo plumber needs exactly one number (minutes between jobs), which the new flat `tenants.travel_buffer_mins` (LK = M16 P2) already delivers on both sides; the matrix is multi-truck routing for a one-truck shop, carrying complexity AND an extra DB round-trip per availability call for zero behavior. **Change:** delete the zone-pair machinery + the per-call `service_zones`/`zone_travel_buffers` fetch, keep only the flat buffer (and remove the dead `slot_start/slot_end` fallback branch in `book_appointment.py:257-263,394-423` while in there).

The Xero+Jobber dual-provider MERGE layer (~1,685 lines) presumes a profile almost no target user has.** **Evidence:** `integrations/xero.py`+`jobber.py` (~1,263) + `customer_context.py:43-116` (field-level `_sources` provenance arbitration). **Why cut:** the merge only pays off for a shop that connects BOTH back-office systems AND has the same customer in both — vanishingly rare for a solo trade (most connect zero or one; Xero adoption among US/CA solo trades is low). **Change:** collapse to a single-provider model (use whichever the tenant connected) and drop the `_sources` arbitration. Core `validate_address` + verdict/components mapping is justified and stays.

The 3-layer triage adds a second LLM provider just to label urgency post-call.** **Evidence:** Layer-2 = a separate Groq LLM + key + silent-failure mode (`lib/triage/layer2_llm.py`), running only post-call (`post_call.py:236`). **Why cut:** the main call LLM (gpt-4.1-mini) already has full conversation context and could emit an urgency tag inline; Layer-1 keywords already catch the canonical emergencies. - **❌ LK-O6. Outbound-minute caps + half-built VIP routing solve problems this size of customer mostly doesn't have.** **Evidence:** `webhook/caps.py` (per-country month caps + Python-side full-table SUM at `:75-84`) guards a ceiling a 1–5-person shop's owner-forwarding minutes will essentially never hit; VIP's second source is stubbed (`webhook/twilio_routes.py:117-123` always returns False). **Why cut:** caps are really Voco-side toll-fraud insurance dressed as a per-tenant feature; VIP is incomplete and rarely configured. **Change:** simplify caps to a hard ceiling (or a DB-side aggregate, not a per-call full-table fetch) and either finish or remove VIP.
