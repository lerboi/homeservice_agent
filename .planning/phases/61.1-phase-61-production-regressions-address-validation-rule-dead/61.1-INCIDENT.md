## Root cause hypothesis (HIGH confidence)

**Phase 61 Plan 04's `_build_address_validation_section` deadlocks the pre-tool address readback.**

The new section (`livekit-agent/src/prompt.py:170-245`) ships a CRITICAL RULE that:

1. Forbids 6 verbatim phrases (`"validated"`, `"verified"`, `"looked up"`, `"matches"`, etc.) **unless the immediately preceding tool return contained `verdict=validated` or `verdict=validated_with_corrections`**.
2. Frames violation as "the worst failure mode in this section."
3. Explicitly licenses silence: **"Silence or a neutral readback is always acceptable; false confirmation is not."** (prompt.py:243-244)

Meanwhile the `book_appointment` tool description (`livekit-agent/src/tools/book_appointment.py:190-204`, also rewritten by Plan 04) tells the model to "Call this after check_slot has confirmed the slot is open and **the caller has acknowledged the name+address readback**."

The agent is now in a chicken-and-egg state during info-gathering:
- It must read back the address to get caller acknowledgment before invoking the tool.
- The CRITICAL RULE flags any address-related utterance without a verdict as the worst possible failure.
- Validation only happens **inside** the tool — there is no verdict yet.
- Silence is the only explicitly-licensed safe fallback.

So the model takes the silence path. No tool invocation. No utterance. Caller hangs up.

This conflicts with the user's own `feedback_livekit_prompt_philosophy.md` memory (LiveKit prompts should be outcome-based, SDK-matched, **non-directive**). The Phase 61 rule is the most directive section in the entire prompt and even endorses non-response.

## Proposed initial fixes

These are starting points for `/gsd:plan-phase 61.1`. The plan should validate via tests and a real UAT call, not just code edits.

### Fix 1 — Scope the rule to post-tool speech only

The opening of `_build_address_validation_section` currently reads as if it governs the entire address conversation. Reframe so it activates only after a tool return.

Suggested opening (EN):
> "After `book_appointment` or `capture_lead` returns, this rule governs how you speak back what the tool found. Before calling the tool, gather the address normally and read back what the caller said to confirm you heard it correctly — that is not 'validated' phrasing."

Symmetrical edit in the ES branch.

### Fix 2 — Remove the silence escape hatch

Drop the line "Silence or a neutral readback is always acceptable; false confirmation is not." Replace with explicit pre-tool guidance that closes the deadlock loop.

### Fix 3 — Soften "worst failure mode" framing

The current "worst failure mode in this section" framing is calibrated for pure post-tool speech but overshoots when applied to the gather/readback step. Either remove the phrase or qualify it as "after a tool return."

### Fix 4 — Tool description: clarify pre-tool readback is allowed

`book_appointment.py:190-204` says "after the caller has acknowledged the name+address readback." Confirm this readback is meant to happen BEFORE the validation tool runs and is not subject to the verdict rule. Consider rewording to "after the caller has acknowledged the address you heard back from them."

Symmetrical edit in `capture_lead.py`.

## Also in scope (advisory findings from 61-REVIEW.md)

These were flagged as warnings during code review and deferred. Folding into 61.1 because they are likely to surface as new regressions if left:

- **WR-01** — `tenant_id=None` is passed to `gmaps_validate_events.tenant_id` which is `NOT NULL`. The constraint violation is silently swallowed by a bare `except Exception:` in `google_maps.py:519-526`. Fix: skip-with-log when tenant_id is falsy. (Defeats D-C2' observability for the calls — early/anonymous — where it matters most.)
- **WR-02** — Empty `address_lines` is misclassified as `unsupported_region` because Google returns 400 INVALID_ARGUMENT and `_is_unsupported_region_400` matches the `invalid_argument` substring. Fix: short-circuit empty `address_lines` to `verdict=error` before HTTP, or tighten the classifier. (Causes false billing rollup + lost Sentry signal.)
- **WR-03** — Success returns are `BOOKED [verdict=...]` / `LEAD CAPTURED [verdict=...]`, not the documented `STATE:... | DIRECTIVE:...` shape. Functionally fine today; brittle if a future prompt rev keys on the `STATE:` prefix.
