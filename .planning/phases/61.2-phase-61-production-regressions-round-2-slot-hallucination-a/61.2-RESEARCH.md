## 2. Failure mode (verified)

**Mechanism:** Gemini 3.1 Flash Live performs server-side VAD on the input audio stream. When VAD detects start-of-speech during an agent generation step, the server cancels the in-flight generation AND discards any pending function calls (Google's Live-tools docs, `_availability_lib.py:30-46` comment). The SDK exposes this only as a `logger.warning("server cancelled tool calls", extra={"function_call_ids": …})` from `livekit.plugins.google.realtime` — there is **no programmatic event** for it. [VERIFIED: research agent dive into 1.5.7 source]

**Compounding factors that make the cascade worse than a single cancel:**

1. **Gemini 3.1 Flash Live is BLOCKING-only for function calling.** Asynchronous function calling is unsupported. The model waits for tool response before continuing — but the server may cancel the wait, leaving the tool result orphaned (`received server content but no active generation` warning, observed at T+22 in the call). [CITED: `ai.google.dev/gemini-api/docs/live-tools`, `_availability_lib.py` module header]

2. **`mutable_chat_context=False` on Gemini 3.1.** No `update_chat_ctx`, no `generate_reply`, no `update_instructions` post-session-start. After cancellation, the agent has no programmatic way to inject "you were interrupted, try again." Recovery must come from Gemini itself. [CITED: `feedback_livekit_prompt_philosophy.md`, `reference_livekit_generate_reply_gemini31.md`, `livekit-plugins-google/realtime_api.py` `mutable = "3.1" not in model`]

3. **Caller-side STT confusion + cancellations compound.** In `AJ_vV4DM5AG9t7W` the agent mis-heard "Cambridge" for "Canberra" (street name). The follow-up correction sequence had two more cancellations during it. Cancellations make every clarification round longer and more error-prone — caller patience runs out before the booking flow completes.

4. **The 1.5.7 patches do NOT fix this.** `livekit-agents==1.5.7` ships `fix: realtime reply generation after interruption` — a one-line `return` guard in `agent_activity._realtime_reply_task:2811` that prevents stale post-interrupt reply scheduling. It addresses a downstream client-side symptom; it does not address the upstream Gemini-server cancel-and-discard behavior. PR #5535 / #5594 add a pausable-output mechanism (output paused on VAD-SOS instead of cancelled, IF `can_pause`-capable output is configured) — this is the only 1.5.7 lever that could plausibly soften the cascade, and it requires opt-in via `RoomOutputOptions`. [VERIFIED: research agent confirmed in upstream diff]

## 4. Fix design (verified-where-possible)

### Fix A — Extend `mute_input_during_tool` to data-fetch tools (HIGH confidence)

The mute pattern is the only known mitigation against in-flight cancellations on 3.1 Flash Live (it physically detaches the input audio so server VAD can't fire). Currently 4 tools mute (the booking-related ones). Three more should: `check_caller_history`, `check_customer_account`, `capture_lead`.

`transfer_call` and `end_call` are intentionally excluded — they tear down the session, so input mute is unnecessary and could mask a caller-cancellation signal during goodbye.

**Diff shape per tool:** add `mute_input_during_tool(deps)` as the first line inside the `@function_tool`-decorated body, identical to `check_day:61`. One import line if not already present.

**Risk:** During a caller-history fetch, the caller is briefly unable to interrupt. ~1.5s is below human-perceptible delay for a "let me look you up" filler. Acceptable tradeoff for eliminating the most common cancellation surface.

### Fix B — Robust unmute lifecycle (MED confidence)

Current listener (`_availability_lib.py:96-114`) matches `listening → speaking` after a fresh `speaking → listening`. In the call AJ_vV4DM5AG9t7W second-`check_day` recovery, the listener never matched — the 15s fallback fired, leaving the unmute to expire mid-recovery while Gemini was still generating.

**Hypothesis:** The recovery generation made a `speaking → listening` transition early (perhaps the cancelled-and-discarded tool wait counted), then a NEW `listening → speaking` for the actual recovery, but no clean `speaking → listening` to close it. The listener saw `saw_fresh_speaking[0] = True` once, then waited indefinitely for the matching listen.

**Two candidate fixes (planner picks one or both):**

1. **Match against function-tool re-execution.** Listen for `function_tools_executed` AFTER the mute was applied. If a NEW tool execution event fires, reset `saw_fresh_speaking` so the lifecycle re-anchors on the recovery.
2. **Raise the fallback for tools with multi-step responses.** The booking section's name+address readback regularly takes 10-14s (per existing comment in `_availability_lib.py:55-67`). 15s is right on the edge. Raise to 25s for `check_day`/`check_slot` callers.

Either keeps the existing event-based-with-timer-cap shape; no new threading.

### Fix C — Server-cancel telemetry log filter (HIGH confidence)

Mirror `_GoodbyeDiagHandler` (agent.py:82-104). Install a `logging.Handler` on `livekit.plugins.google.realtime` that watches for messages containing `"server cancelled tool calls"` AND `"received server content but no active generation"`. Each match increments a counter on `diag_record[0]`:
- `server_tool_cancellations` — int
- `orphaned_server_content` — int

These flow through `_flush_goodbye_diag` to the `[goodbye_race]` log line + Sentry breadcrumb at call close. Post-call telemetry can then aggregate cancellation rate per call / per tenant / per model.

**Behavior change:** None. This is observability only.

### Fix D (DROPPED from this phase) — Pausable RoomOutputOptions

The 1.5.7 PR #5535/#5594 mechanism (output pauses on caller speech instead of cancelling) requires:
- `RoomOutputOptions` configured at `session.start(...)` (currently not configured at all, agent.py:830-840)
- Audio output that supports `can_pause` (uncertain whether Gemini Live's audio output qualifies)

Even if it works, it operates on the *output* side, not the *server-side* tool cancellation. Lower-priority lever; defer to a follow-up phase or to a separate spike.
