## The new failure

> agent: *"Got it, unit 0704. So, just to confirm, you're available on Thursday at 10 AM?"*

> agent: *"My apologies, I misspoke. Is there a particular day that would work for you?"*

And critically: **`tool_call_log_tail: []`** — zero tools invoked in the entire 132-second call.

What's broken:
1. **Zero tool invocations.** Neither `check_availability` nor `book_appointment` nor `capture_lead` was called. The agent is conversational without ever progressing to actual tool use.
2. **Hallucinated slot time.** The agent confirmed *"Thursday at 10 AM"* — a slot the caller never gave (caller explicitly denied: *"I never said that"*). With no `check_availability` call, the agent has no real slot data to anchor against.
3. **No fabricated booking.** Caller correction prevented the worst case — agent didn't claim a booking happened. But the call ended with no booking and no captured lead, so the outcome is the same as the 07:09 deadlock from Phase 61.1's perspective: caller hangs up unhelped.

## Root cause hypothesis (MEDIUM-HIGH confidence)

The Phase 61.1 prompt rewrite **may** have softened the tool-invocation pressure too much. The original Phase 61 Plan 04 description was directive:

> "Speak a short filler phrase first ('Let me get that booked in for you'), then invoke in the same turn. Do not speak 'booked'/'confirmed' or the appointment time as a settled fact before this tool returns success."

Phase 61.1 reframed this and the address-validation rule to be less directive (per `feedback_livekit_prompt_philosophy.md`). The reframing was correct — the OLD framing caused the deadlock. But the NEW framing may have removed too much of the implicit pressure to invoke tools, leaving the agent in a "keep talking, never commit" failure mode.

Alternative hypothesis: this is the documented Gemini 3.1 Flash Live behavior where the model prefers text continuation over function calls under ambiguous prompts (see user memory `reference_livekit_generate_reply_gemini31.md` and the `'gemini-3.1-flash-live-preview' has limited mid-session update support` warning that fires on every call).

These hypotheses are NOT mutually exclusive — the fix may need to address both.

## Proposed initial fixes (starting points only)

### Fix candidate 1 — Restore tool-invocation pressure without re-introducing deadlock

The Phase 61 Plan 04 description had load-bearing language about WHEN to invoke. Phase 61.1 softened it. Re-add invocation pressure scoped to the post-info-gathering phase:

> "Once you have street, postal code, day preference, and urgency, invoke `check_availability`. Do not propose specific slot times before this tool returns. Speak a short filler ('Let me check our calendar') first, then invoke in the same turn."

Apply same pattern to `book_appointment` after `check_availability` returns.

### Fix candidate 2 — Anti-hallucination rule for slot times

Add a new prompt section (parallel to the address-validation rule):

> "SLOT TIMES — CRITICAL RULE: Slot times (days, hours, AM/PM) are facts that come from `check_availability` returns or from the caller's verbatim statement. Never propose a slot time that did not come from one of those two sources. If unsure, ask the caller what works for them."

### Fix candidate 3 — Investigate Gemini 3.1 Flash Live tool-use reliability under realtime

The `received server content but no active generation` warning fires consistently. Phase 64 (LiveKit pipeline migration) is the long-term answer per existing roadmap. Phase 61.2 may need a tactical workaround in the meantime.
