### New / Revised Decisions

#### D-01-rev (Fix shape — REVISED)
Ship **Fix A + Fix B + Fix C** as defined in `61.2-RESEARCH.md` § 4. All land together as one coherent code rev on a single feature branch in `livekit-agent/`. No prompt edits. No tool-signature changes.

#### D-A-01 (Fix A scope)
Add `mute_input_during_tool(deps)` as the first line of the body of:
- `livekit-agent/src/tools/check_caller_history.py` (inside `check_caller_history` async fn)
- `livekit-agent/src/tools/check_customer_account.py` (inside `check_customer_account` async fn — verify name during plan read-first)
- `livekit-agent/src/tools/capture_lead.py` (inside `capture_lead` async fn — verify name during plan read-first)

DO NOT add to:
- `livekit-agent/src/tools/transfer_call.py`
- `livekit-agent/src/tools/end_call.py`

Reason: terminal tools intentionally end the session. Muting during teardown could mask caller cancellation signal.

#### D-B-01 (Fix B unmute lifecycle approach)
Two changes to `_availability_lib.py:49-146` `mute_input_during_tool`:

1. **Raise `_TOOL_MUTE_FALLBACK_S` from 15.0 to 25.0.** The existing 15s comment notes the booking-section name+address readback regularly takes 10-14s. 15s leaves no margin for cancellation-recovery generation. 25s is the new ceiling. (Tradeoff: in the failure mode where Gemini's recovery never produces a clean speak/listen cycle, the caller waits 10s longer before they can speak again. Acceptable — the cascade is the higher-impact failure.)
2. **Reset `saw_fresh_speaking[0]` on `function_tools_executed`.** Subscribe to the `function_tools_executed` event inside `mute_input_during_tool`. On any new tool execution AFTER mute, reset `saw_fresh_speaking[0] = False` so the lifecycle re-anchors on the recovery generation. Unsubscribe in the same `_unmute_logic()` cleanup block as the existing state-change listener.

Skip a more invasive refactor (e.g. tying the unmute to specific generation IDs) — stays inside the existing event-shaped pattern, single-file edit.

#### D-C-01 (Fix C telemetry)
Mirror the existing `_GoodbyeDiagHandler` (agent.py:82-104). New class `_ServerCancelHandler(logging.Handler)`:
- Installed on `logging.getLogger("livekit.plugins.google.realtime")` AND `logging.getLogger("livekit.plugins.google")`
- Watches `record.getMessage()` for substrings:
  - `"server cancelled tool calls"` → increment `_diag_record[0]["server_tool_cancellations"]` (default 0)
  - `"received server content but no active generation"` → increment `_diag_record[0]["orphaned_server_content"]` (default 0)
- Removed in `_flush_goodbye_diag` cleanup (same finally block that removes `_GoodbyeDiagHandler`)

The two new fields land in the `[goodbye_race]` log line + Sentry breadcrumb at call close. Post-call telemetry can aggregate cascade rate per call.

NO behavior change. Pure observability.

#### D-12-rev (Live UAT — MANDATORY GATE, success criteria updated)
Place a live LiveKit SIP test call against the test tenant AFTER Fixes A+B+C are Railway-deployed. Success requires:

1. **Cascade rate down.** `server_tool_cancellations` count from `[goodbye_race]` log line for the new call is < 5 (the AJ_vV4DM5AG9t7W baseline of 5 cancellations / 230s).
2. **No mid-utterance fragmenting in transcript.** No agent turn in `transcript_structured` ends mid-word OR is followed by a sibling agent turn starting with a leading-space continuation.
3. **Tool flow completes.** Agent reaches a `check_day` or `check_slot` invocation cleanly and either books OR captures a lead. NO ship if the call hangs up like AJ_vV4DM5AG9t7W did.

Pre-fix baseline (AJ_vV4DM5AG9t7W): 5 cancellations, multiple fragmented turns, not_attempted, caller hung up. Anything strictly better is improvement; criteria 2 and 3 are the must-have evidence the cascade is contained.

Resume signal: `merge` (UAT passed) or `gap` (UAT failed; planner triages whether 61.3 or back to 61.2 plan adjustments). Same posture as Phase 63/63.1.
