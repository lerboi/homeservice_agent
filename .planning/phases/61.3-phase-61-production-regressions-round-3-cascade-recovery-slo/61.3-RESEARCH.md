## Summary

Phase 61.3 adds one mechanism: when the 25s mute fallback fires (indicating Gemini-server TTS stalled and never produced a clean speak→listen cycle), the agent reconstructs the last tool's STATE string and replays it as a synthetic `FunctionCallOutput` via `update_chat_ctx` before unmuting. This closes the slot-inversion failure observed in UAT call `AJ_5NcSoiaZGZTJ` where `check_day` returned `STATE:day_has_slots count=9` but the regenerated agent response told the caller "we don't have anything open tomorrow."

All three critical claims from CONTEXT.md have been verified against the installed SDK (livekit-agents 1.5.7, livekit-plugins-google installed at the same path). The `tool_results` send at `realtime_api.py:637-638` is unconditional. `generate_reply()` is gated and raises `RealtimeError` for `gemini-3.1-flash-live-preview`. The fallback branch in `mute_input_during_tool` is the only async location where the recovery can land.

One significant gap surfaces from inspecting the source: **`_tool_call_log` entries do NOT currently store the raw STATE+DIRECTIVE return string.** The log captures `{"name": ..., "success": ..., "result": ..., "date": ...}` — metadata only. The planner must decide how to source the STATE string for replay: either (a) add a `"state_str"` field to `log_tool_call` calls in each tool file, or (b) add a `deps["_last_tool_state"]` key that tools write their return value into before returning. Option (b) is narrower and is the recommended approach.

**Primary recommendation:** Add `deps["_last_tool_state"] = <return_value>` assignment in each data-fetch tool immediately before returning, then read `deps.get("_last_tool_state")` in the fallback branch of `_unmute_logic()` for the replay construction.

The public property `realtime_llm_session` is defined at `agent_activity.py:352`:

### 3. Source of the last tool's STATE string and call_id

[VERIFIED: installed check_day.py, check_slot.py, _availability_lib.py]

**CRITICAL FINDING: `_tool_call_log` does NOT store the STATE+DIRECTIVE return string.**

Inspecting `check_day.py:107`:
```python
log_tool_call(deps, {"name": "check_day", "success": True, "result": "has_slots", "date": date})
return (
    f"STATE:day_has_slots date_label={date_label} count={len(all_slots)}"
    " | DIRECTIVE:confirm the day is open; ask for a concrete hour; do not mention times."
)
```

The `log_tool_call` captures metadata but NOT the return string. The returned STATE+DIRECTIVE string goes directly to the SDK and is not stored anywhere in `deps`.

Similarly for `check_slot.py:161-171` — the `log_tool_call` entry captures slot metadata, not the raw return value.

**Consequence for the plan:** The plan MUST add a mechanism to capture the STATE string before it is returned. Two options:

**Option A (recommended — narrow scope):** Add `deps["_last_tool_state"] = <return_val>` immediately before each `return` statement that produces a STATE+DIRECTIVE string in the data-fetch tools. This can be done with a thin wrapper helper in `_availability_lib.py`:

```python
def _record_and_return(deps: dict, state_str: str, call_id: str, name: str) -> str:
    """Store the last tool's STATE string + call_id for cascade-recovery replay."""
    deps["_last_tool_state"] = state_str
    deps["_last_tool_call_id"] = call_id
    deps["_last_tool_name"] = name
    return state_str
```

Tools would then: `return _record_and_return(deps, f"STATE:day_has_slots ...", call_id, "check_day")`.

**The `call_id` acquisition problem:** The current tool function signatures use `@function_tool` decorator. The `RunContext` passed to tools gives access to the underlying function call ID. The tool receives a `RunContext[VocoAgent]` argument (named `ctx` by convention). The current function signatures in the availability tools accept `(ctx, deps)` or similar. The `FunctionCall.call_id` is available via `ctx.function_call_info.call_id` or `ctx.raw_kwargs` — this needs confirmation against the installed SDK.

[PARTIAL — needs verification] Check the `RunContext` API:

```python
# agent_activity.py pattern for how tool context is constructed
# RunContext contains function_call_info with the call_id
```

**Alternative — simpler:** Store the call_id via the `FunctionToolsExecutedEvent`. The event at `agent_activity.py:3340-3372` fires AFTER the tool completes and includes `function_calls` list. The listener `_on_tools_executed` in `mute_input_during_tool` already receives this event. Add a side-effect to the listener to store the last `call_id` and `name`:

```python
def _on_tools_executed(event):
    try:
        saw_fresh_speaking[0] = False
        # Store last call_id for replay
        if event.function_calls:
            last_call = event.function_calls[-1]
            deps["_last_tool_call_id"] = last_call.call_id
            deps["_last_tool_name"] = last_call.name
    except Exception:
        pass
```

This approach doesn't require modifying every tool file. However, the STATE string (the output) is still not stored.

**Pragmatic resolution:** The planner should add `deps["_last_tool_state"] = return_val` in the data-fetch tools (check_day, check_slot, next_available_days, check_caller_history, check_customer_account, capture_lead), and use `_on_tools_executed` to capture the `call_id` + `name`. This splits the concern cleanly.

### 6. `_diag_record` extension surface (conditional-emit pattern)

[VERIFIED: agent.py:136-148]

The existing conditional-emit pattern in `_ServerCancelHandler.emit`:

```python
def emit(self, record: logging.LogRecord) -> None:
    try:
        msg = record.getMessage()
        if "server cancelled tool calls" in msg:
            self._diag_record[0]["server_tool_cancellations"] = (
                self._diag_record[0].get("server_tool_cancellations", 0) + 1
            )
        elif "received server content but no active generation" in msg:
            self._diag_record[0]["orphaned_server_content"] = (
                self._diag_record[0].get("orphaned_server_content", 0) + 1
            )
    except Exception:
        pass
```

The pattern: key initialized via `.get(key, 0) + 1` so the key is only present in the JSON when count > 0. This preserves the existing `[goodbye_race]` JSON shape for calls without cascade events.

**New counters follow the same pattern, but they are incremented from within `_unmute_logic()` (async context via `deps["_diag_record"]`), NOT from a `logging.Handler`.** The counter update in `_attempt_tool_result_replay`:

On error:

The same `diag_record` list is the one shared between `deps["_diag_record"]` and the `diag_record` closure in `agent.py` (line 415: `"_diag_record": diag_record`). They are the same list reference, so incrementing via `deps` automatically flows into `_flush_goodbye_diag`.

## Architecture Patterns

### Replay helper function structure

```python
# Inside _availability_lib.py — new async helper

async def _attempt_tool_result_replay(
    deps: dict,
    session,          # AgentSession — from mute_input_during_tool closure
    mute_set_at_ms: int,
) -> None:
    """Best-effort replay of the last tool's STATE string after a stall.

    Called from _unmute_logic()'s TimeoutError branch (D-03, D-05, D-07).
    Fires BEFORE set_audio_enabled(True) (D-06).
    Increments diag counters via deps["_diag_record"] (D-08).
    """
    diag = deps.get("_diag_record")

    # Stall confirmation: no audio frames advanced since mute (D-04)
    last_frame_ms = diag[0].get("last_audio_frame_at") if diag else None
    stall_confirmed = (last_frame_ms is None or last_frame_ms <= mute_set_at_ms)
    if not stall_confirmed:
        return  # audio advanced — not a stall, skip replay

    state_str = deps.get("_last_tool_state")
    call_id = deps.get("_last_tool_call_id")
    tool_name = deps.get("_last_tool_name")
    if not (state_str and call_id and tool_name):
        return  # no last tool result available to replay

    # Increment recovery attempt counter (D-08 conditional-emit)
    if diag:
        diag[0]["stalled_generation_recoveries"] = (
            diag[0].get("stalled_generation_recoveries", 0) + 1
        )

    try:
        rt_session = None
        if session._activity is not None:
            rt_session = session._activity.realtime_llm_session

        if rt_session is None:
            raise RuntimeError("no active rt_session for replay")

        from livekit.agents import llm as _llm
        synthetic_output = _llm.FunctionCallOutput(
            call_id=call_id,
            name=tool_name,
            output=state_str,
            is_error=False,
        )
        chat_ctx = rt_session.chat_ctx.copy()
        chat_ctx.items.append(synthetic_output)
        await rt_session.update_chat_ctx(chat_ctx)

        logger.info(
            "[tool_mute] stall-recovery replay sent id=%d tool=%s state=%.80s",
            deps.get("_tool_mute_id", 0), tool_name, state_str,
        )

    except Exception as e:
        logger.warning("[tool_mute] stall-recovery replay failed: %s", e)
        if diag:
            diag[0]["stalled_generation_replay_failed"] = (
                diag[0].get("stalled_generation_replay_failed", 0) + 1
            )
```

## Common Pitfalls

### Pitfall 1: `call_id` ordering — tool output logged before listener fires

**What goes wrong:** The tool writes `deps["_last_tool_state"]` on return. The `_on_tools_executed` listener fires AFTER the tool exits (at `agent_activity.py:3372`). So `_last_tool_state` is set BEFORE `_last_tool_call_id`. In normal operation this is fine. But if the stall fires and the fallback triggers BEFORE `_on_tools_executed` has a chance to run (race condition in the asyncio event loop), `deps["_last_tool_call_id"]` may not be set yet.

**How to avoid:** In `_attempt_tool_result_replay`, the null guard `if not (state_str and call_id and tool_name): return` handles this case — if `call_id` is not yet set, skip replay silently.

**Warning signs:** `stalled_generation_replay_failed` counter increments, log line "no last tool result available to replay".

### Pitfall 2: Replay with a stale `call_id` from a prior tool call

**What goes wrong:** `deps["_last_tool_call_id"]` persists across tool calls. If the sequence is `check_caller_history` → `check_day` (stalled), the `call_id` should be for `check_day`. But if `_on_tools_executed` fired for `check_caller_history` and then the `check_day` stall hits BEFORE `_on_tools_executed` fires for `check_day`, the `call_id` is from `check_caller_history`.

**How to avoid:** The stall guard `stall_confirmed = (last_frame_ms is None or last_frame_ms <= mute_set_at_ms)` filters for the current mute window. If `check_day` is what's stalled, `mute_set_at_ms` is set at `check_day`'s mute call, and the stall check is scoped to that window. The `_last_tool_call_id` mismatch would only cause Gemini to ignore the replay (wrong call ID) — not a catastrophic failure. Best-effort (D-07) covers this.

### Pitfall 3: `update_chat_ctx` without items in the diff

**What goes wrong:** If the synthetic `FunctionCallOutput` already exists in `rt_session.chat_ctx` (e.g., from the original tool execution path), `compute_chat_ctx_diff` returns an empty diff, `append_ctx.items` is empty, and `get_tool_results_for_realtime` returns `None`. The replay silently no-ops.

**How to avoid:** Check if `_last_tool_state` is different from what's already in the chat context. Alternatively, always replay on stall (idempotent at the Gemini server level — sending a duplicate tool result causes Gemini to regenerate, which is the desired behavior). The SDK does NOT deduplicate tool responses at the client.

**Note:** The diff computation is in `update_chat_ctx` via `compute_chat_ctx_diff(self._chat_ctx, chat_ctx)`. If the item was never added (because the tool execution was cancelled before the tool result was processed by `agent_activity.py:3358`), the diff WILL include the new item.

### Pitfall 4: `session._activity` is `None` at replay time

**What goes wrong:** If the session is already closing (call disconnected), `session._activity` may be `None`.

**How to avoid:** The null guard in `_attempt_tool_result_replay` (`if session._activity is not None`) handles this. The try/except wrapper (D-07 best-effort posture) catches any `AttributeError` if the race is tight.

## Open Questions

1. **`call_id` availability timing race**
   - What we know: `_on_tools_executed` fires at `agent_activity.py:3372` after tool completion; `deps["_last_tool_state"]` is set by tool before returning; the fallback fires after 25s.
   - What's unclear: Is there a case where the 25s timer fires before `_on_tools_executed` has executed (i.e., tool executed but event loop hasn't processed the emission yet)?
   - Recommendation: This race is unlikely at 25s window, but the null guard on `call_id` makes it safe regardless. Planner can accept the best-effort posture.

2. **Whether to add `deps["_last_tool_state"]` in all tools or only the stall-prone ones**
   - What we know: Tools that exercise the blocking wait pattern (check_day, check_slot, next_available_days) are the stall-prone ones. check_caller_history, check_customer_account, capture_lead also use mute but complete faster.
   - What's unclear: Cost/benefit of modifying all 6 vs. only the 3 most stall-prone.
   - Recommendation: Add to all 6 data-fetch tools for consistency. The change is mechanical (1-2 lines per return path per tool).

3. **Whether `FunctionToolsExecutedEvent.function_calls[-1].call_id` is the right call_id for a stall**
   - What we know: A server-cancelled tool call means the original `FunctionCall.call_id` is what was cancelled. The `_on_tools_executed` event fires for the COMPLETED execution, so its `call_id` is from the SUCCESSFUL tool run.
   - What's unclear: If the sequence is tool-completes → server-cancels-the-response (not the tool call itself), does the `FunctionCall.call_id` from `_on_tools_executed` match what Gemini server would accept as a `FunctionResponse.id`?
   - Recommendation: The UAT failure (call `AJ_5NcSoiaZGZTJ`) shows the server cancelled `function_call_id fc_15328661595426966818`. The tool DID execute (check_day returned count=9), then the server cancelled the response generation. The `FunctionCall.call_id` from `_on_tools_executed` should be the same ID the server used. Best-effort — if Gemini rejects it, the replay simply doesn't take effect and `stalled_generation_replay_failed` increments.

4. **Whether the `check_day` tool's `RunContext` gives direct access to `call_id`**
   - What we know: `@function_tool` decorated tools receive a `RunContext` arg. `RunContext.function_call_info` may expose `call_id`.
   - What's unclear: The exact API — needs one line of verification against the installed `RunContext` type.
   - Recommendation: Use the `_on_tools_executed` listener approach (captures from `FunctionToolsExecutedEvent.function_calls[-1].call_id`) rather than modifying tool signatures. This is cleaner and consistent.
