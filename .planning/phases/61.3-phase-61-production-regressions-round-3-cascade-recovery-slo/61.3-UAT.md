### Root cause — residual audio frame after mute

`_availability_lib.py:211-218` (`_attempt_tool_result_replay`):

```python
last_frame_ms = diag[0].get("last_audio_frame_at") if diag else None
stall_confirmed = (
    last_frame_ms is None or last_frame_ms <= mute_set_at_ms
)
if not stall_confirmed:
    return  # silent skip
```

The mute fired at `33.797` while the agent was still mid-filler. The agent
finished the filler 15ms later at `33.812`, and the LiveKit audio pipeline
stamped `last_audio_frame_at ≈ 33.812` for the trailing frame of that filler.

`33.812 > 33.797` → `last_frame_ms <= mute_set_at_ms` is False →
`stall_confirmed = False` → recovery skipped silently. The audio-frame check
treated the residue from the pre-mute filler as "Gemini is responding to the
tool result" when in fact Gemini had not produced a single frame after the
mute.

This is a 15-30ms race window that closes any time `mute_input_during_tool`
fires while the agent is finishing a "let me check…" filler — i.e. on every
tool call where the prompt asks the agent to acknowledge the request before
calling the tool, which is the dominant pattern in production prompts.

### Verdict: gap

The cascade described in `project_phase_61_cascade_failure_mode` memory and the
slot-hallucination failure mode from Phase 61.2's UAT (call AJ_5NcSoiaZGZTJ)
both reproduced on the deployed Plan 03 code. The recovery hook is wired and
deploys correctly, but the stall-detection predicate has a 15-30ms
false-negative window that hides the cascade from `_attempt_tool_result_replay`.

This is **not a Phase 60.4-style timezone issue, not a Phase 61.2 prompt issue,
and not a deployment miss**. It is a stall-detection predicate bug introduced in
Plan 03 itself — the truth source for "did Gemini speak" was the wrong signal
(audio-frame timestamp instead of agent_state speak-transition).

### Resolution path — in-flight fix (Option 1)

A follow-up commit on Plan 03 changes the stall-detection predicate to use the
existing `saw_fresh_speaking[0]` closure flag from `_on_state_change` as the
primary signal, with the audio-frame check downgraded to belt-and-braces with a
250ms grace to absorb residual frames.

```python
# in _unmute_logic timeout branch:
await _attempt_tool_result_replay(
    deps, session, mute_set_at_ms, saw_fresh_speaking[0]
)

# in _attempt_tool_result_replay:
GRACE_MS = 250
last_frame_ms = diag[0].get("last_audio_frame_at") if diag else None
audio_quiescent = (
    last_frame_ms is None or last_frame_ms <= mute_set_at_ms + GRACE_MS
)
stall_confirmed = (not saw_fresh_speaking) and audio_quiescent
if not stall_confirmed:
    return
```

`saw_fresh_speaking[0]` is True iff the agent has freshly transitioned
`listening → speaking` after the mute — i.e. iff Gemini has actually started
delivering audio in response to the tool result. Audio-frame timestamps are
jittery (residual frames from pre-mute filler), but the state-change event is
a clean monotonic signal.

A new semantic test at `tests/test_cascade_recovery_residual_audio.py`
reproduces this exact race and asserts replay still fires; the original
6 substring-grep invariants (`tests/test_cascade_recovery_invariants.py`)
remain green.
