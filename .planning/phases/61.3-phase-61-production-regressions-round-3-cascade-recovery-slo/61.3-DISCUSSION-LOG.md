| Option | Description | Selected |
|--------|-------------|----------|
| B1 | Synthetic user-turn replay via `generate_reply()` | (initial recommendation; PARTIALLY FALSIFIED — `generate_reply` is gate-blocked on 3.1 in 1.5.7, confirmed at `realtime_api.py:707-715`) |
| B2 | Pin tool result via `update_chat_ctx` | (initially rejected as "gate-blocked"; RESEARCH OVERTURNED THIS — `tool_results` send at `realtime_api.py:637-638` is UNCONDITIONAL, not gated) |
| B3 | Prompt-level rule "if last tool returned has_slots, never assert no-slots without re-checking" | (rejected — Phase 61.x has shown prompt rules cannot prevent server-VAD cancels; SDK does not re-attach tool results to regeneration) |

| **B1+B2 hybrid** | **Stall detection in async layer (post-fallback in `_availability_lib.py`) + tool-result replay via `update_chat_ctx` tool_results path (the unconditional-send unlock)** | ✓ |

**User's choice:** Go with the validated approach.

**Notes:** Memory `reference_livekit_generate_reply_gemini31` confirmed accurate in 1.5.7 (`generate_reply` blocked). But the broader claim that "`update_chat_ctx` is capability-gated closed on 3.1" was partially incorrect — only the conversational-turns half is gated; the `tool_results` half is unconditional. This is THE unlock that makes recovery viable on `gemini-3.1-flash-live-preview`. Replay must fire BEFORE `set_audio_enabled(True)` to avoid VAD race (`silence_duration_ms=2500` gives only 2.5s grace).
